# 1 LCEL表达式缺陷与扩展
  1.1.LCEL与AgentExecutor的局限性：
  LCEL:线性流程  转态管理复杂 工具的使用不直观
  AgentExecutor:复杂性 动态路由 状态持久性 过度封装 黑盒不可控
  
  1.2.认识 图与状态机 :
  状态机是一个记录有限行为状态的盒子.
  baby_status={
     "饥饿程度":"饿",
     "精神状态":"清醒",
     "体感温度":"热",
  }
  任何具有状态的事物都有 初始状态 最终状态.
  不同状态之间是可以通过事件进行转换的,转换和事件是确定性的.
  
  有了状态和N个事件之后,可以把相关联的事件连接起来,
  状态作为事件的输入和输出,输出的状态作为下一个事件的输入,
  通过约束和条件设置初始状态与最终状态,
  这样就构成一张图,图中每个节点为事件,
  边(通信逻辑)连接节点与节点,状态就是节点与边的输入模式.
  
  LangGraph用于构建图结构,对比LCEL和AgentExecutor的优点:
  1.图结构支持更复杂的非线性流程和条件分支.
  2.内置强大的状态管理机制,无缝的管理多轮对话状态.
  3.简化工具集成和使用,通过上下文动态选择和调用工具.
  4.内置状态持久性机制,支持长时间运行的对话,可随时暂停或恢复.
  5.组件仍然是Runnable组件,是LCEL的扩展.
  
# 2.LangGraph介绍与基础组件:
  2.1langgraph介绍与功能:
  一个构建具有状态,多角色应用程序的库,用于创建智能体和多智能体工作流.
  核心优势:循环,可控制性和持久性,允许定义设计循环,条件判断的流程.
  其组件都是最基础的,允许开发者实现对应用程序流程和状态精细控制,自由度极高.
  可以便捷集成持久化方案,任意节点终端交互,修改状态，可以在没有Langchain环境下单独使用.

  主要功能:循环分支,持久化,人机交互,流支持,与langchain/langsmith集成

  2.2.langgraph基础组件使用:
  模块安装:pip install -U langgraph 

  1.状态: 节点和边的输入,可以是字典或Pydantic模型,包括图的模式(数据结构),以及如何更新状态的归纳函数.
  2.节点: 同步或异步的Python函数,参数1:state状态,参数2:config(Runnable运行的配置),返回值一般都是状态.
  3.边: 定义路由逻辑,节点之间如何传递,传递给谁,图节点的开始与结束,一个节点可以设置多条边,
      如果有多条边,每边连接的节点都会并行运行.


# 3.LangGraph条件边与循环流程实现工具调用Agent
  3.1.条件边与循环流程:
  langGraph中边的种类有4种:
  普通边: 一个节点到下一个节点  
         add_edge()
  条件边: 调用一个函数来确定下一个要跳转的节点 
         add_conditional_edge(
          source:条件边的起始节点名称,该节点运行完后会执行条件边
          path:确定下一个节点是什么的可运行对象或函数
          path_map:可选参数,字典,返回的path与节点名称的映射关系,默认是节点名称
          then:可选参数,path节点之后统一选择节点,设置后不需要为后续的每个节点都设置一个统一的关联节点
         )
  入口边: 用户输入首先调用的节点,图结构的开始节点
  条件入口边: 调用一个函数来确定用户输入到达时首先调用的节点,通过函数来确定图结构的开始节点
  
  循环:没有专属的循环设置函数,只需要通过add_edge()将两个节点串起来即可.
      循环流程都需要一个条件边去跳出循环,死循环会导致应用崩溃,极大消耗系统资源

# 4.LangGraph实现ReACTive架构Agent
  4.1.预构件的ReACT智能体:
  除了使用节点,边,状态这些基础组件来构建Agent,还可以使用预构建的代理来快速创建智能体,
  如:ReAct智能体 或者 工具调用智能体


  4.2.其他的预构建组件:
  MessageState:替代之前一直使用的自定义State
  ToolNode节点:替代之前的tool_executor函数,自动执行状态中最后一条消息中的工具调用信息,
               输出ToolMessage列表
  validationNode:用于检测State状态信息中,最后一个AIMessage中所有的工具请求是否正确,
                 以验证LLM的结构化输出是否正确,实例化时需要传递Pydantic的Model作为需要校验的类.
  InjectedState:用于在工具上注入数据状态,工具中也可以获取到图架构应用中的状态数据,
                工具中使用Annotated装饰的参数不会被视为工具参数,LLM在执行函数调用时,
                也不会生成该参数。一般使用较少,需要将工具与图结构分离,工具中如果需要状态数据内容
                则可以去使用

# 5.LangGraph图结构应用程序删除消息的使用技巧
  5.1.更新删除与归纳函数:
  可以使用RemoveMessage装饰符配合add_messages()函数实现删除消息列表中的某条消息,
  或是修改消息列表中的某条数据,逻辑是add_messages()底层会对类型为RemoveMessage的消息执行删除操作.
  要删除消息时,节点返回RemoveMessage实例,并传递消息ID即可.

  自定以函数节点,在获取AI消息后,根据需要修改AIMessage的content

  5.2.过滤与修剪消息:
  随着对话内容的增加,在langGraph中需要对消息进行过滤和修剪.
  过滤和修剪不会更改状态,而是在调用LLM时,只传递特定条数的消息或按token长度进行修剪.


# 6.LangGraph检查点实现记忆持久化功能
  6.1.MemorySaver检查点与线程:
  检查点用于记录或标记程序在某个阶段的状态,用于在程序运行出现问题时,
  回溯到特定状态,或在图执行的过程中奖任意一个节点的状态进行保存.
  其逻辑原理类似于游戏在每个关卡后保存一个检查点/存档点,可以从同的检查点/存档点重新启动游戏.

  langGraph中持久化的方式就是检查点,而且还与线程ID有关,检查点存储的是特定线程的数据状态,
  考虑到一个应用的多次独立对话功能.好比一个游戏可以有多个玩家,每个玩家都有独属的存档记录.

  6.2.其他检查点:

# 7.LangGraph图结构断点 实现Agent与人进行交互
  7.1.人在环路与断点: 
  Human-in-the-loop HIL,在一些特定领域的Agent中,需要人类允许或指示才能进入下一步,HIL最重要的部分就是断点.
  断点建立在检查点之上,检查点在每个节点执行后保存图的状态,
  而且可以使得图执行以特定点暂停,等待人为批准后,从最后一个检查点恢复执行.

  7.2.在图结构上更新对应状态:
  除了通过节点更新数据状态,还可以在检查点模式基础上,
  使用get_state()与update()方法更新状态(特定线程中)

# 8.LangGraph子图架构实现AI工作流
   8.1.子图结构与应用场景:
   对于更为负责的系统,子图是一个非常有用的设计原则,允许在图的不同部分创建和管理不同的状态,
   实现类似多智能体亦或者AI工作流之类的功能,功能之间相互独立隔离,最终组成一个大型复杂应用.

   LangGraph的节点可以是任意的Python函数或者Runnable组件,图编译后就是一个Runnable组件,
   可以将一个图程序作为另一个图程序的节点,从而实现子图,将一些功能相近的节点单独组装成图,单独进行状态管理.

   入口图视为父级,子图作为入口图的节点,子图状态继承于父图状态,且再拥有自己的私有状态.

   如果定义了多边,则必须定义归纳函数,因为多边是并行的,如果没有归纳函数,数据会直接覆盖,
   且并行顺序是不确定的,没有归纳函数可能会出现数据相互覆盖问题,
   langgraph中如果有多边,且没有为状态的每个字段定义归纳函数,会直接报错.
